# core.py 工程事实整理算法代码解读指南（由浅入深）

> 适用对象：`src/engineering_facts/core.py`
> 阅读目标：看懂「工程事实整理」这个确定性算法是如何一步步把上游算法产物变成一份可追溯、可复算的 `engineering_facts.json`，以及它新增的「公用工程能源整理与折算」是怎么工作的。

## 第 0 步：先建立"一句话"全局认知（1 分钟）

在看任何细节之前，先用一句话锁定这个文件是干什么的：

> **`core.py` 是一个确定性的数据整理管道：输入一个上游算法产物目录，输出一份结构化、可复算、可溯源的 `engineering_facts.json`，并在最后对设备公用工程消耗进行整理与标准煤/标准油折算。**

它**不做**这些事（这些是后续阶段或别的角色的职责）：

- 不调用 LLM，不重写方案描述；
- 不生成项目名称、项目编号；
- 不做用户确认；
- 不判断章节是否完备、不写报告正文；
- 不做能源定价/成本核算——只把公用工程物理量折算成标准煤/标准油当量，不碰价格。

记住这条边界，很多函数设计的原因你立刻就能理解。

- 对外唯一入口（API）：[execute](../../src/engineering_facts/core.py#L131-L180)
- 最终产物落盘：[_write_artifact](../../src/engineering_facts/core.py#L1949-L1958)

> 停下来想一想：如果这个模块"不生成项目名称"，那么最终 JSON 里 `unit.name` 放的是什么？（答案：上游的 `plant_name` 装置名称，见 [_build_unit](../../src/engineering_facts/core.py#L551-L568)）

## 第 1 步：从入口函数开始，倒着读主流程（最重要）

理解一个"管道型"代码的最佳入口，不是从第一行开始，而是从 `execute` 开始——它是唯一对外入口，也是整个主流程的"目录"。

### 1.1 主流程 = 五个阶段

打开 [execute](../../src/engineering_facts/core.py#L131-L180)，它按顺序做了五件事：

```text
校验输入
  → 发现来源
  → 加载并校验来源
  → 构建事实
  → 清洗 + 落盘
```

对应代码顺序：

| 阶段 | 函数 | 干什么 |
|---|---|---|
| 1. 校验输入 | `_validate_request` | 强制 `root`，允许可选 `file_overrides` / `construction_unit` |
| 2. 读取来源 | `_load_host_directory_sources` | 按标准文件名清单（可被 `file_overrides` 覆盖）经 HostClient 读取宿主逻辑目录下的来源文件 |
| 3. 加载/校验 | `_validate_source_set`、`_warn_related_source_gaps` | 至少识别一个来源，并提示关联资料缺口 |
| 4. 构建事实 | `_build_facts` | 把各来源映射成 11 个一级字段，含派生事实与公用工程能源 |
| 5. 清洗/落盘 | `_clean`、`_write_artifact` | 剔除禁止字段，写 JSON，返回 URI/schema/媒体类型 |

### 1.2 一个贯穿全文件的约定：错误用 `diagnostics` 累积，而不是抛异常

你会注意到几乎所有函数都带一个 `diagnostics: list[Diagnostic]` 参数。这个项目的设计是：

- 遇到问题**不直接 `raise`**，而是往 `diagnostics` 里追加一条 `Diagnostic`；
- 每个阶段结束后用 `_has_fatal` 检查有没有 `fatal` 级诊断，有就提前返回失败。

这就是为什么 [execute](../../src/engineering_facts/core.py#L131-L180) 里会看到多处 `if _has_fatal(diagnostics): return _failed_response(...)`。

> 停下来想一想：`fatal` 和 `warning` 两种诊断有什么区别？它们最终分别去了哪里？（提示：`fatal` 会让整个流程失败返回；`warning` 会随成功结果一起返回，但都不写入 `engineering_facts.json`。）

## 第 3 步：核心功能模块识别（六个模块）

结构是"骨架"，模块是"器官"。这个文件可以拆成六个功能模块，每个模块解决一个问题。

### 模块 1：来源读取与识别（"这是什么文件"）

核心函数：`_load_host_directory_sources`、[_classify_json](../../src/engineering_facts/core.py#L357-L392)

- 按固定清单 `HOST_DIRECTORY_SOURCE_FILES` 逐个角色尝试读取默认文件名；`file_overrides` 可覆盖单个文件名。
- 每个槽位对应唯一角色，读取后仍用**内容签名**（结构特征）复核识别结果，不匹配直接报错；Markdown 诊断报告用标题特征判断 `plant_diagnosis`。

### 模块 2：输入与来源校验（前置防御）

核心函数：`_validate_request`、`_validate_source_set`、`_warn_related_source_gaps`。

- 不固定具体必需来源，适配设备级、装置级以及后续系统级、全厂级改造。
- 至少要识别到一个受支持来源；缺少关联专业结果只返回 warning，不阻断整理。
- 同一角色识别到多个文件仍是致命错误，因为算法无法确定应采用哪份数据。

### 模块 3：事实映射（把来源字段搬到目标结构）

核心函数：`_build_*` 系列。这是最大的模块，本质是"字段搬运 + 精简 + 溯源"，不做推断（除派生事实外）。

### 模块 4：方案选择（`adopted_scheme` 的唯一来源）

核心函数：[_build_scheme_sections](../../src/engineering_facts/core.py#L824-L920)、[_selected_names](../../src/engineering_facts/core.py#L923-L937)、[_scheme_matches](../../src/engineering_facts/core.py#L940-L943)

- 「最终采用方案」**只**来自 `scheme.json.user_selected`，绝不从拓扑、推荐、候选反推。这是本文件最重要的业务约束之一。

### 模块 5：派生事实（可复算的年化量）

核心函数：[_build_derived_facts](../../src/engineering_facts/core.py#L1061-L1130)、[_annualize](../../src/engineering_facts/core.py#L1170-L1175)

- 做了"计算"：把 kg/h 流量折算成 t/a；把外部进料折算成原辅料年消耗。且保留公式和输入值，保证可复算、不冒充上游名义产能。

### 模块 6：公用工程能源整理与折算（新增）

核心函数：[_build_utility_consumption_summary](../../src/engineering_facts/core.py#L1178-L1222)、[_build_energy_conversion](../../src/engineering_facts/core.py#L1511-L1564)

- 从设备专业事实中识别循环冷却水、导热油、电力、蒸汽等公用工程消耗，汇总成可复算年量；
- 再依据 `src/engineering_facts/rules/energy_conversion_rules.json` 折算为标准煤（tce）或标准油（toe）。

> 停下来想一想：为什么方案评分（score）不进结果，而公用工程折算结果却进结果？（提示：评分是算法中间产物、不是"事实"；公用工程折算是确定性、可复算的事实，且保留了规则来源与公式。见 `FORBIDDEN_KEYS` 与 `_scheme_evaluation`、`_build_energy_conversion`。）

## 第 4 步：关键算法 / 逻辑解释（逐个击破）

这一节挑出六个最容易卡住的逻辑，把它讲透。

### 4.1 来源识别：按"结构签名"的顺序匹配

[_classify_json](../../src/engineering_facts/core.py#L305-L340) 从特定到一般地做了一串 `if` 判断：

```text
plant_info   → 顶层有 plant_info 子对象
plant_level  → 同时有 design_case / retrofit_case / components
scheme       → schemaVersion == "topology_retrofit_v1" 且 schemeKind == "diagnosis"
retrofit_topology → 有 nodes / edges / schemeInfo
retrofit_equipment → 有 equipment 且是 list
tower_result  → 有 separator + combined_schemes
reactor_result→ 有 reactors + combined_schemes
new_device_params → 有 reactors + separators
```

关键点：**顺序很重要**。比如 `reactor_result` 和 `new_device_params` 都含 `reactors`，靠 `combined_schemes` 这个额外特征来区分先后。

### 4.2 方案选择：`user_selected` 必须"精确且唯一"匹配

[_build_scheme_sections](../../src/engineering_facts/core.py#L824-L920) 的逻辑分三步：

1. `_selected_names` 把 `user_selected` 归一化成名字列表；
2. 在 `candidates + user_candidates` 两个池子里找匹配（[_scheme_matches](../../src/engineering_facts/core.py#L940-L943) 按 name/schemeId/scheme_id/id 匹配）；
3. 结果分三种：
   - 没找到 → `fatal: USER_SELECTED_NOT_FOUND`
   - 找到多个 → `fatal: USER_SELECTED_AMBIGUOUS`
   - 恰好一个 → 记入 `adopted_scheme.schemes`

> 停下来想一想：为什么"候选池重名"也被当作致命错误？这在业务上保护了什么？

### 4.3 派生事实：固定的年化公式

[_build_derived_facts](../../src/engineering_facts/core.py#L1061-L1130) 对单位是 `kg/h` 的流股做：

```text
年化量(t/a) = flow_value(kg/h) × annual_operating_hours(h/a) / 1000
```

并且每个结果对象都带 `input`（原始流量值、单位、运行时）、`formula`（公式）、`source_refs`（溯源），这样任何人在任何时间都能复算。外部进料还会再生成一份 `annualized_material_consumption` 原辅料年消耗。

### 4.4 清洗机制：`_clean(keep_top=True)` 是"定形"关键

[_clean](../../src/engineering_facts/core.py#L1928-L1946) 做三件事：

1. 剔除 `FORBIDDEN_KEYS` 里的字段；
2. 剔除键名含 `llm` 的字段；
3. 清空 `None`、空 dict、空 list。

而 [_build_facts](../../src/engineering_facts/core.py#L487-L533) 最后调用 `_clean(facts, keep_top=True)`，**只保留 `TOP_LEVEL_KEYS` 里的 11 个一级键**。这是保证产物 Schema 稳定的最后一道闸门。

注意一个容易混淆的点：`FORBIDDEN_KEYS` 里有 `energy`，但产物里却有 `derived_facts.energy_conversion`。这是因为 `energy` 黑名单防的是上游原始 `energy` 块泄露，而折算结果放在 `derived_facts.energy_conversion` 这个允许字段里。

### 4.5 公用工程识别：只从设备事实中抽取，反应器只认"已选方案"

入口 [_build_utility_consumption_summary](../../src/engineering_facts/core.py#L1178-L1222) 调用 [_extract_equipment_utilities](../../src/engineering_facts/core.py#L1225-L1302) 扫描设备段。识别规则有三类：

1. **`utility` 子对象**：直接把 `{...utility}` 当作一条公用工程记录；
2. **`utility_medium` / `heat_medium` 字段**：配合质量流量 `*_kg_h`、功率 `*_kw`、压力/温度等字段组成一条记录；
3. **热负荷线索**：只有 `duty`/`heat_duty` 等而没有明确介质时，标记为 `medium = "热负荷线索"`，作为无法折算的线索保留。

它**只在 `equipment` 段内扫描**，避免把工艺流股里的 `medium` 误当成公用工程。反应器还特别用 [_selected_reactor_utility_rows](../../src/engineering_facts/core.py#L1305-L1338) 只认 `selected_combined_scheme` 指向的方案，防止把未采用的候选方案消耗也算进去。

[_normalize_utility_item](../../src/engineering_facts/core.py#L1366-L1421) 再把介质归一化（导热油/循环冷却水/电力/蒸汽/热负荷线索），并计算可复算年量：

```text
有质量流量 → mass_flow_kg_h × hours / 1000 → t/a
有功率     → power_kw × hours → kWh/a
有显式年量 → 直接采用 annual_quantity
```

最后 [_dedupe_utility_items](../../src/engineering_facts/core.py#L1424-L1456) 把同一设备/工况/介质/物理量合并来源，避免重复计量。

> 停下来想一想：为什么"只认已选反应器方案"很重要？如果误把候选方案也统计进来，会对公用工程汇总和能源折算造成什么影响？

### 4.6 能源折算：规则驱动，折算不了的明确标 `blocked`

[_build_energy_conversion](../../src/engineering_facts/core.py#L1511-L1564) 的流程：

1. `_select_energy_conversion_type` 从上游 hints 中探测采用「标准油」还是默认「标准煤」；
2. `_load_energy_rules` 读取 `energy_conversion_rules.json`；
3. 对 `utility_consumption_summary.items` 里的每一项调用 `_convert_utility_item`：
   - 普通介质按 `medium_code` / `medium_name` 查规则索引；
   - 蒸汽走 [_match_steam_rule](../../src/engineering_facts/core.py#L1732-L1764) 按压力/等级匹配；
   - 用 [_harmonize_annual_unit](../../src/engineering_facts/core.py#L1767-L1780) 统一单位后乘以折算系数；
4. 结果按工况汇总 `totals_by_condition`。

折算不了的项会被 `_conversion_blocked` 标记为 `blocked` 并给出原因（如 `physical_quantity_missing`、`conversion_factor_missing`、`unit_mismatch`、`steam_pressure_or_grade_missing`）。整体状态 `_conversion_status` 分三种：`calculated` / `partial` / `blocked`。

> 停下来想一想：为什么折算结果要保留 `rule_id`、`coefficient`、`coefficient_unit` 和 `source`（标准出处/条文）？（提示：折算系数是外部规则、可能随规范修订变化，保留出处才能复算和审计。）

### 5.2 变量命名：语义清晰 + 类型注解

- 复数名词表示集合：`payloads`、`sources`、`diagnostics`、`candidates`、`streams`、`items`、`totals`。
- 单数 + 具体含义表示元素：`source_type`、`stream_id`、`selected_name`、`medium_code`、`conversion_type`。
- `source_refs` / `source_id` / `source_type` 反复出现，是本项目的"溯源"核心概念，务必分清：
  - `source_id`：来源角色（如 `plant_info`）；
  - `source_type`：同上，来源角色；
  - `source_refs`：挂在每个事实字段上的引用列表，回答"这行数据来自哪、哪个字段"。

### 5.3 通用约定

- 使用 `from __future__ import annotations`，函数签名里写完整类型注解；
- 返回结构一律是"纯 dict/list"，不返回自定义类实例（`Source`、`Diagnostic` 只在内部流转，最终 `as_dict` 转成 dict）；
- 防御式取值：大量 `X.get("y") or {}`、`(X or [])`，配合最终的 `_clean` 兜底。

> 停下来想一想：为什么内部用 `Source`/`Diagnostic` 类，但对外返回的都是纯 dict？（提示：便于被 JSON 序列化，也把内部模型与外部契约解耦。）

## 第 6 步：代码整体实现思路梳理（数据流串起来）

把所有模块串成一条数据流，你就能"一眼看到底"。

### 6.1 数据流图

```text
业务输入 request
   │  { root, file_overrides?, construction_unit? }
   ▼
校验 → 通过？
   │ 否 → 返回 failed(artifact=null, diagnostics)
   ▼ 是
按标准文件名清单经 HostClient 读取 root 下的来源文件
   ▼
校验至少一个有效来源，提示关联资料缺口
   ▼
构建 facts: { meta, sources, basic_info, unit, component_catalog,
               process, diagnosis, scheme_analysis, adopted_scheme,
               equipment,
               derived_facts: {
                   annualized_stream_quantities,
                   annualized_material_consumption,
                   utility_consumption_summary,
                   energy_conversion,
               } }
   ▼
清洗 _clean(keep_top=True)
   ▼
落盘 engineering_facts.json
   ▼
返回 { status, artifact, summary, diagnostics }
```

### 6.2 六条设计原则（理解所有"为什么"的钥匙）

1. **确定性**：同样的输入必然产生同样的输出，所以不调 LLM、不改写描述；
2. **最小输入**：业务上只强制 `root` 一个字段，其余来源文件按标准文件名清单自动尝试读取；
3. **不越界**：只整理"事实"，不生成项目名、不判断章节、不写报告；能源只做物理量折算、不碰价格；
4. **可溯源**：每个关键字段带 `source_refs`，回答"从哪来"；能源折算还带 `rule_id`/`source`，回答"按哪条规则折算"；
5. **防御式**：`fatal/warning` 分级的 diagnostics + 前置校验 + `_clean` 终稿清洗；
6. **规则外置**：折算系数放在 `src/engineering_facts/rules/energy_conversion_rules.json`，代码只负责读取与计算，规则修订无需改代码。

## 附录 A：输入输出契约（字段、含义、必填性）

> 入口函数：[execute](../../src/engineering_facts/core.py#L131-L181)，签名 `execute(request: dict, artifact_dir=None)`。
> `artifact_dir` 是运行时参数（默认写仓库根目录 `report_output_dir`），**不属于业务输入**。

### A.1 输入

| 字段 | 含义 | 必填 | 说明 |
| --- | --- | --- | --- |
| `root` | 宿主文件服务中的来源逻辑目录前缀 | 必填 | string，来源文件应位于该目录下 |
| `file_overrides` | 来源文件名覆盖 | 可选 | dict，仅当来源文件不使用标准文件名时填写，值为相对 root 的宿主逻辑路径 |
| `construction_unit` | 建设单位名称 | 可选 | string，空值归一化为空字符串 |

> 请求里出现任何未声明字段（如 `root` 之外多传 `foo`）都会产生 `fatal` 诊断。

### A.2 输出：成功

`status = "completed"`

| 字段 | 含义 |
| --- | --- |
| `artifact.path` | 产出的 `engineering_facts.json` 的宿主逻辑路径 |
| `artifact.schema_version` | 工程事实 schema 版本，固定 `"2.0"` |
| `artifact.media_type` | `"application/json"` |
| `engineering_facts` | 完整工程事实对象（11 个一级字段，见本指南数据流） |
| `summary` | 少量计数汇总（见下表） |
| `diagnostics` | 诊断列表（仅 `warning` 级随成功结果返回） |

`summary` 各字段：

| 字段 | 含义 |
| --- | --- |
| `source_count` | 识别到的来源文件数 |
| `equipment_count` | 设备对象目录条数 |
| `candidate_count` | 候选方案数 |
| `user_candidate_count` | 用户候选方案数 |
| `adopted_scheme_count` | 已采用方案数 |
| `selected_names` | 已采用方案名称列表 |
| `optimized` | 是否优化（来自已采用方案） |
| `derived_fact_count` | 派生事实总条数 |
| `annualized_stream_quantity_count` | 年化流股量条数 |
| `annualized_material_consumption_count` | 年化原辅料消耗条数 |

### A.3 输出：失败

`status = "failed"`

| 字段 | 含义 |
| --- | --- |
| `artifact` | `null` |
| `summary` | 空对象 `{}` |
| `diagnostics` | 含 `fatal` 级诊断（如 `INVALID_REQUEST`、`SOURCE_LOCATION_NOT_FOUND`、`NO_RECOGNIZED_SOURCES` 等） |
