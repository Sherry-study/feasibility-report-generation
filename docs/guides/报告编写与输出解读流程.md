# 可研报告编写 Tool 代码解读流程

> 目标对象：`src/report_generation` 目录下的 Python 包。
> 本指南由浅入深，分七个阶段带你读懂这份代码：先理解“它要解决什么问题”，再逐步深入到“每一步是怎么实现的”。

---

## 第 0 步：先建立一个“电梯演讲”式的整体认知

在逐行读代码之前，先回答三个问题：**它是什么、输入什么、输出什么**。

**它是什么**
一个「确定性」的报告编排 Tool。它自己不调用 LLM、不联网、不用缓存，而是把一份工业装置技术改造项目的《可行性研究报告》拆解成：
- 一些可以**直接从工程事实算出**的内容（表格、段落）；
- 另一些**必须交给 Agent（LLM）去撰写或汇总**的内容。

然后把这两部分“打包”成工作包，等 Agent 完成后再把结果“合并”成最终的 Markdown / DOCX 报告。

**输入（4 类）**
| 输入 | 文件 | 作用 |
| --- | --- | --- |
| 工程事实 | `engineering_facts.json` | 已经核实、结构化的工程数据（装置、工艺、设备、方案等） |
| 报告模板 | `templates/report_template.json` | 定义报告有哪些章节、每章放什么块 |
| 章节规则 | `rules/chapter_rules.json` | 定义需要 Agent 撰写的章节“怎么写、查什么、禁止写什么” |
| 标准库 | `rules/standards_library.json` | 编制依据/标准规范的分组清单 |

**输出**
- `prepare` 阶段：`work_package.json`（工作包）+ `chapter_contexts/*.json`（各章节事实切片）
- `finalize` 阶段：`可行性研究报告_初稿.md` + `可行性研究报告_初稿.docx`

**核心设计理念**：把“能确定的”和“需要智能的”明确分开。能确定的用纯函数算，需要智能的封装成结构化的“任务”交给 Agent，最后再拼装。这样保证了**可复现性**（相同输入 → 相同输出）。

## 第 1 步：代码结构分析（从“文件地图”入手）

先看目录，不看代码，建立文件级地图：

```
src/report_generation/
├── __init__.py               # 对外导出 execute、DEFAULT_ARTIFACT_DIR
├── core.py                   # 核心：prepare / finalize 两大流程（最重）
├── context_builder.py        # 工程事实的校验与“按需裁剪”（切片）
├── deterministic_builders.py # 从事实直接构建“确定性"块（表格/段落）
├── template_loader.py        # 加载并校验模板 + 规则 + 标准库
├── exporters.py              # 把报告模型导出为 Markdown / DOCX
├── templates/report_template.json
└── rules/
    ├── chapter_rules.json
    └── standards_library.json
```

**依赖关系（谁调用谁）**：

```
__init__.py（execute）
        │
        ▼
      core.py  ────────────────►  context_builder.py
        │  │                        ▲
        │  ├────────────────────►  deterministic_builders.py（也依赖 context_builder）
        │  └────────────────────►  template_loader.py ──► context_builder / deterministic_builders
        │
        ▼
     exporters.py
```

三个要点：
1. `core.py` 是调度中枢，其它模块都是被它调用的“零件”。
2. `context_builder.py` 提供基础能力（读路径、校验根字段），被多人复用。
3. `template_loader.py` 依赖 `context_builder` 的 `FACT_ROOTS` 和 `deterministic_builders` 的 `BUILDER_NAMES`，用于“交叉校验”。

**建议读法**：先读 `__init__.py`（最短，几行）和 `core.py` 的入口 `execute`，再按需下钻到其它模块。

## 第 2 步：核心功能模块识别（把“零件”分门别类）

按职责，整个包可以归纳为 **5 个功能模块**：

1. **入口与调度模块**
   - `__init__.py`：对外导出 `execute` 与 `DEFAULT_ARTIFACT_DIR`。
   - `core.py: execute`：分发到 `_prepare` 或 `_finalize`，统一捕获异常返回 `failed`。

2. **输入治理模块（工程事实）**
   - `context_builder.py`：校验工程事实的“固定根契约”，并支持按“点分路径”读取/裁剪数据。

3. **模板与规则模块**
   - `template_loader.py`：加载模板和两条规则文件，严格校验后把“引用”展开（标准组展开为列表、契约挂到章节上）。

4. **确定性内容生成模块**
   - `deterministic_builders.py`：根据模板声明的块 + 事实，产出段落/列表/表格，不经过 LLM。

5. **导出模块**
   - `exporters.py`：把最终的抽象“报告模型”（项目名 + 章节 + 块列表）渲染成 Markdown 和 DOCX。

识别技巧：**一个文件通常围绕一个“数据形态”或“生命周期阶段”来组织**。抓住每个文件“输入什么数据结构、输出什么数据结构”，模块边界就清晰了。

## 第 3 步：关键算法 / 逻辑解释（挑最有信息量的几个）

这一节是理解深度的关键。不建议直接背所有函数，而是理解下面几个贯穿全局的“机制”。

### 3.1 固定根契约（fixed root contract）
`context_builder.py` 里 `FACT_ROOTS` 定义了工程事实顶层**只能且必须**有哪些字段，共 11 个根字段：

```python
FACT_ROOTS = [
    "meta", "sources", "basic_info", "unit", "component_catalog",
    "process", "diagnosis", "scheme_analysis", "adopted_scheme",
    "equipment", "derived_facts",
]
```

每个根字段还配了 `ROOT_TYPES`（预期顶层类型：dict 或 list）和 `ROOT_DEFAULTS`（空值时的默认形态）。`validate_fact_roots` 依次检查：

1. 顶层必须是 object；
2. 根字段不能缺失、也不能多余；
3. 每个根字段类型符合 `ROOT_TYPES`；
4. `meta.schema_version` 必须为 `"2.0"`。

```python
def validate_fact_roots(facts): ...   # 缺失/多余/类型不对/schema 不符都报错
```

**为什么重要**：这是整个系统的“信任边界”。只要这里校验通过，后续所有 `get_path`、`build_fact_slice` 都能安全地按约定取数据。它类似于数据库的 schema；`meta.schema_version == "2.0"` 则是这份 schema 的“版本锁”，保证上下游契约可预期。

### 3.2 点分路径读取与切片（`get_path` / `build_fact_slice`）
用字符串 `"unit.design_case.products"` 来表达嵌套取值路径：

```python
def get_path(data, path):   # 逐层按 "." 拆开取 dict 键，取不到返回 None
def build_fact_slice(facts, paths):  # 按多条路径“抠出”一个章节需要的事实子集
```

两个边界要记住：
- `get_path` **刻意不支持列表索引遍历**（如 `"process.design.streams[0].flow"` 不合法），任何一段不是 dict 或键不存在就返回 `None`；
- `build_fact_slice` 的每条路径必须以 `FACT_ROOTS` 中的根字段开头，否则直接报 `unsupported fact path`，从源头挡住越界读取。

**为什么重要**：每个章节只拿到它需要的事实切片（`fact_slice`），实现章节之间的**隔离**，避免把无关/敏感数据塞给 Agent。

### 3.3 确定性块 vs Agent 槽位（两分法）
`core.py: _prepare` 遍历每个章节，判断它属于哪种：

- `deterministic_blocks`：由 `build_blocks` 直接算出（静态文本、标准引用、事实值、条件文本、确定性表格）。
- `agent_slot`：`_has_block(section, "llm_section")` → `"writing"`；`_has_block(section, "synthesis_section")` → `"synthesis"`；否则 `None`。

对于既没确定性块、又没 Agent 槽位的**叶子章节**，用 `fallback` 兜底。这条“叶子章节”的判定见下一小节。

### 3.4 叶子章节判定（`_leaf_section_ids`）
一个章节如果它的 id 是其他章节 id 的前缀（如 `"1.1"` 是 `"1.1.1"` 的前缀），则它是**父章节**；否则是**叶子**。

```python
parents = {sid for sid in ids
           for cand in ids
           if cand != sid and cand.startswith(f"{sid}.")}
return set(ids) - parents
```

**为什么重要**：只有叶子章节才有实际内容兜底的必要。父章节（如 `1.` 总论、`1.1` 概述）往往是纯层级节点，内容由其子章节撑起。

### 3.5 研究任务聚合（`_register_research_task`）
多个撰写章节如果共享同一个 `research_group`（如 `market_research`），会被合并成一个「研究任务」：

```python
task = research_task_groups.setdefault(group, {...})  # 首次出现建任务
task["target_section_ids"].append(section_id)         # 追加目标章节
```

**为什么重要**：研究（联网检索市场、企业信息等）是昂贵的，按“研究主题”聚合可以避免为每个章节重复检索同一主题。

### 3.6 确定性摘要（`_build_deterministic_summaries` / `_deterministic_section_summary`）
有些章节本身不需要 Agent 撰写，但会被某个“合成章节”当作素材引用。此时直接从它的确定性块里提炼摘要：

- `paragraph` → 若文本等于 fallback 归入 `unresolved_items`，否则归入 `key_facts`
- 列表 → 归入 `key_facts`（最多 12 条）
- 表格 → 输出“表号 + 表题”及“表头：单元格”文本（最多 8 行）

此摘要最终给合成章节的 Agent 使用，避免它去读原始大块内容。

### 3.7 finalize 的回退机制（`_finalize`）

Agent 工作结果有三种互斥输入路径（`_agent_work_results`）：

- inline `work_results` 对象：直接使用该对象；
- `work_results_uri`：从该 URI 指向的 JSON 文件读取；
- 两者都未提供：使用空结果继续生成（不失败），并写入 `WORK_RESULTS_NOT_PROVIDED` warning 诊断，说明本次报告为不完整初稿。

同时传入 `work_results` 和 `work_results_uri` 会直接报参数冲突错误（两者是同一类数据的两种传入方式，不允许两份结果不一致）；传入非法内容也会失败，而不是静默降级为空结果。

对每个有 Agent 槽位的章节，尝试从结果中取合法块：

```python
agent_blocks = _valid_agent_blocks(result)  # 校验 + 清洗白名单块
if agent_blocks is None:                     # 缺失/非法
    fallback_count += 1
    blocks.append({"type": "paragraph", "text": section["fallback"]})
```

即：**Agent 产出不合格时，绝不产出乱码，而是优雅降级到该章节预设的 `fallback` 文本**，并记录一条 warning 诊断。

### 3.8 模板引用解析与白名单校验（`_resolve_template_references` / `_validate_block`）
`template_loader.py` 在返回模板前做两件关键的事：

1. **引用展开**：`_resolve_template_references` 把模板里的“引用”落成可执行的数据——
   - `standards_reference` 块的 `group` → 从标准库取出对应列表，写入 `block["items"]`；
   - `llm_section` / `synthesis_section` 块的 `contract_ref` → 从章节规则深拷贝对应契约，挂到 `section["contract"]`（后续 `prepare` 从这里读 `fact_paths`、`research_group`、`source_section_ids` 等）。
2. **白名单严格校验**：`_validate_block` 用 `ALLOWED_BLOCK_TYPES` 限定块类型，并为每种块类型声明“允许字段集合”，多余字段/缺失必填/非法 builder 都会报错。此外还要求 `contract_ref` 与所在 `section_id` 完全一致、`research_group` 与 `research_objectives` 必须成对出现或同时为空。

**为什么重要**：模板本质是一份“声明式配置”，只有在校验通过后才可信。引用展开让模板保持简洁（只写 `group` / `contract_ref`），而校验保证了配置不会悄悄跑偏。

## 第 4 步：变量与函数命名规范说明

这份代码的命名高度一致，掌握规律后阅读成本会大幅下降。

### 4.1 函数命名
- **模块私有的内部函数**统一用下划线前缀：`_prepare`、`_finalize`、`_uri_to_path`、`_valid_agent_blocks`。
- **对外公开的函数**不带下划线：`execute`、`load_template`、`build_blocks`、`normalize_fact_roots`。
- **动词开头**表达“做什么”：
  - `build_*`：构造数据（`build_fact_slice`、`build_blocks`、`build_table`）
  - `validate_*`：校验（`validate_fact_roots`、`_validate_template`）
  - `normalize_*`：规范化（`normalize_fact_roots`、`_normalize_section_order`）
  - `load_*` / `_load_json`：读取
  - `export_*`：导出
  - `get_*` / `_*_by_*`：取值或映射（`get_path`、`_streams_by_id`、`_equipment_by_bucket`）

### 4.2 常量命名
模块级常量全部大写蛇形：
`FACT_ROOTS`、`ROOT_TYPES`、`ROOT_DEFAULTS`、`BUILDER_NAMES`、`ALLOWED_BLOCK_TYPES`、`SUMMARY_FIELDS`、`MEDIA_TYPE`。

### 4.3 类型注解
广泛使用现代 Python 类型注解，是理解数据结构的重要“文档”：

```python
def build_fact_slice(facts: dict[str, Any], paths: list[str]) -> dict[str, Any]: ...
def _agent_slot(section: dict[str, Any]) -> str | None: ...
```

读代码时**优先看函数签名里的参数和返回类型**，能快速判断“吃什么、吐什么”。

### 4.4 命名语义
- `facts` = 规范化后的工程事实
- `raw_facts` = 未规范化的原始读取结果
- `fact_slice` = 某章节的事实子集
- `section_contract` = 某章节的撰写/合成契约
- `package` / `work_package` = 工作包
- `results` / `work_results` = Agent 产出
- `_fmt` / `_text` / `_value` / `_unit` = 一组“取值/格式化”工具函数，通常成对出现

## 第 5 步：代码整体实现思路梳理（把流程串起来）

### 5.1 端到端数据流（最重要的一张图）

```
[工程事实]──┐
            │  normalize_fact_roots   （校验+深拷贝）
            ▼
       规范化 facts ──► build_fact_slice（按章节裁剪）
            │                    │
            │                    ▼
            │            chapter_contexts/*.json
            ▼
     build_blocks（确定性块）
            │
            ▼
     遍历模板 sections ◄── load_template(模板+规则+标准库)
            │
            ├─ 确定性块 → sections
            ├─ llm_section   → writing_tasks   + 研究任务聚合
            └─ synthesis_section → synthesis_tasks + 确定性摘要
            │
            ▼
      work_package.json  ──(交给 Agent)──►  work_results.json
                                              │
                                              ▼
                                          _finalize
                                            │ 校验字段 / 结果映射
                                            │ 拼装块，缺失用 fallback
                                            ▼
                          report 模型 ──► exporters ──► .md + .docx
```

### 5.2 分成两个阶段理解

**阶段 A：`prepare`（准备）**
目标：把所有需要的信息“装进”一个工作包，等待 Agent 干活。
1. 读取并规范化工程事实；
2. 加载模板（含规则、标准库解析）；
3. 遍历每个章节：算确定性块、判断 Agent 槽位；
4. 生成 writing/synthesis/research 三类任务和确定性摘要；
5. 写出 `work_package.json`。

**阶段 B：`finalize`（定稿）**
目标：接收 Agent 结果，拼装成最终报告。
1. 读取工作包 + 工作结果，校验字段；
2. 结果列表转 `{section_id: result}` 映射；
3. 逐章节拼块：确定性块 + Agent 块（非法则 fallback）；
4. 导出 Markdown 和 DOCX。

### 5.3 一句话总结
> 这个 Tool 是一个 **“确定性骨架 + Agent 填空 + 严格校验 + 优雅兜底”** 的报告组装流水线。它把“写报告”这件复杂的事，拆成了“能算的算清楚、要查的打包成任务、写完的校验拼装”三个可控环节。

## 第 6 步：推荐的循序渐进阅读顺序

按下面顺序读，每一步都在上一步基础上加一点新知识：

1. `__init__.py` → `core.py: execute`
   建立“从 Python API 到 execute”的第一印象（约 5 分钟）。
2. `core.py` 的 `execute` + `_prepare`
   抓住主流程和“确定性与 Agent 两分法”。
3. `context_builder.py`
   理解“根契约 + 点分路径”这套数据基础。
4. `template_loader.py`
   理解模板/规则怎么被校验和展开，明白 `section["contract"]` 从哪来。
5. `deterministic_builders.py`
   看确定性表格具体怎么从事实算出来（挑 `_scale_table`、`_material_balance`、`_equipment_by_bucket` 三个即可）。
6. `core.py` 的 `_finalize` 和 `_*_summary` / `_valid_agent_blocks`
   理解结果如何校验、拼装、兜底。
7. `exporters.py`
   看最终如何渲染成 Markdown / DOCX。

**阅读时的小技巧**
- 遇到 `_xxx` 函数，先看它前面的中文 docstring/注释，再看函数签名，最后看实现。
- 把 JSON 文件当"数据字典"随手查：模板决定"章节有哪些块"，规则决定"章节怎么写"，标准库决定"依据有哪些"。

## 附录 A：输入输出契约（字段、含义、必填性）

> 入口函数：[execute](../../src/report_generation/core.py#L61-L88)，签名 `execute(request: dict, artifact_dir=None)`。
> `artifact_dir` 是运行时参数（默认写仓库根目录 `report_output_dir`），**不属于业务输入**。

本 Tool 通过 `request["operation"]` 区分两个阶段，两个阶段的输入字段不同。

### A.1 输入：`operation = "prepare"`

| 字段 | 含义 | 必填 | 说明 |
| --- | --- | --- | --- |
| `operation` | 操作类型 | 必填 | 固定取字符串 `"prepare"` |
| `engineering_facts_uri` | 工程事实 JSON 的位置 | 必填 | `file://` URI 或本地路径，指向工程事实整理 Tool 产出的 `engineering_facts.json` |
| `report_context` | 报告上下文对象 | 可选 | 仅允许一个字段 `project_name`，缺省为 `{}` |

`report_context` 子字段：

| 字段 | 含义 | 必填 | 说明 |
| --- | --- | --- | --- |
| `project_name` | 显式项目名称 | 可选 | 不传时按「建设单位 + 装置名称 + 技术改造项目」等规则回退生成 |

> 出现任何未声明字段（如 prepare 请求里多传了 `foo`）都会直接报错返回 `failed`。

### A.2 输入：`operation = "finalize"`

| 字段 | 含义 | 必填 | 说明 |
| --- | --- | --- | --- |
| `operation` | 操作类型 | 必填 | 固定取字符串 `"finalize"` |
| `work_package_uri` | 工作包位置 | 必填 | prepare 阶段产出的 `work_package.json` 的 URI/路径 |
| `work_results_uri` | 工作结果位置 | 必填 | Agent 产出的 `work_results.json` 的 URI/路径 |

### A.3 输出：prepare 成功

`status = "prepared"`

| 字段 | 含义 |
| --- | --- |
| `artifact.uri` | 产出的 `work_package.json` 的 file URI |
| `artifact.schema_version` | 工作包 schema 版本，固定 `"1.0"` |
| `artifact.media_type` | `"application/json"` |
| `summary.research_task_count` | 研究任务数 |
| `summary.writing_task_count` | 撰写任务数 |
| `summary.deterministic_summary_count` | 确定性摘要章节数 |
| `summary.synthesis_task_count` | 合成任务数 |
| `diagnostics` | 诊断列表（prepare 阶段一般为空） |

### A.4 输出：finalize 成功

`status = "completed"`

| 字段 | 含义 |
| --- | --- |
| `artifacts.docx` | 报告初稿 DOCX 的 file URI |
| `artifacts.markdown` | 报告初稿 Markdown 的 file URI |
| `markdown_content` | 报告正文 Markdown 全文（字符串） |
| `summary.section_count` | 报告章节总数 |
| `summary.fallback_section_count` | 因 Agent 结果缺失/非法而回退到 `fallback` 的章节数 |
| `diagnostics` | 诊断列表（如 `SECTION_FALLBACK` 告警） |

### A.5 输出：失败

`status = "failed"`

| 字段 | 含义 |
| --- | --- |
| `artifact` / `artifacts` | 均为 `null` |
| `summary` | 空对象 `{}` |
| `diagnostics` | 含 `fatal` 级诊断（如 `REPORT_TOOL_FAILED`） |
